\section{整体架构}

本文的标注系统分三层，如图\ref{fig:architecture}所示。

第一层是数据合成层。Code2Logic 从游戏源代码里提取逻辑结构，按模板生成 QA。这一层的作用是验证方法论可行：不需要人工标注，从代码就能自动产出高质量问答数据。第二层是场景理解层，把 Code2Logic 的模板化方法搬到真实 3D 场景。这里的难度远大于游戏世界——物体不是代码定义的坐标，而是从 RGB-D 数据里分割出来的；空间关系不是写死在规则里的，要靠模型推断。第三层是真值验证层，用 Isaac Sim 生成合成场景作为"标准答案"，定量地衡量 Concept-Graphs 标注的准确度。三层之间是递进关系：游戏方法在第一层被验证可行，在第二层被迁移到真实世界，在第三层被合成真值校准。

\section{Concept-Graphs 标注管线}

\subsection{六步管线}

管线的数据流如图\ref{fig:pipeline}所示。

\input{figures/fig_pipeline}

第一步用 GradSLAM\cite{gradslam} 从 RGB-D 序列和相机轨迹重建三维点云地图，以 5 帧为步长处理约 400 个关键帧。第二步用 Grounded-SAM\cite{grounded_sam} 在每个关键帧上做检测和分割，这一步是整个管线中最耗时的，单场景约需 25 分钟。第三步用 CF-SLAM 把二维分割投影到三维空间，经过重叠检测和 DBSCAN 聚类后，输出每个物体的三维位置、包围盒尺寸和语义特征向量。

第四步由 LLaVA v1.5 7B\cite{llava} 对每个物体的裁剪区域生成自然语言描述。裁剪区域以物体投影中心为锚点，边长取包围盒对角线长度的 1.5 倍。如果同一个物体在多个帧中被观测到，取置信度最高的那一帧的裁剪区域作为输入。第五步是整个管线的核心：用 llama.cpp 在 GPU 上跑 qwen2.5:3b\cite{qwen2_5}，同时做两件事——优化 LLaVA 的原始描述，以及推理物体间的空间关系。这一步是管线中唯一涉及大语言模型推理的环节。第六步按统一的 JSON 模板生成 Target Perception、Spatial Reasoning 和 Scene Comprehension 三类 QA 数据。

\subsection{Prompt 设计}

LLaVA 原始输出的典型问题是描述太笼统（"自然光洒满空间"）和输出被截断（"es are all white..."）。针对这两个问题，本文重新设计了第五步的 prompt，核心改动有三个方面。

第一个方面是强制模型输出 class 字段，要求显式给出物体的类别名称。这直接解决了旧 prompt 输出"全是氛围、没有物体"的问题：模型不再能含糊地描述"一个明亮的空间"，它必须给出 door、table、sofa 这样的具体标签。第二个方面是设置禁用词汇表，直接禁止 light、atmosphere、depth、shadow 等十几个场景级描述词。这是一个简单粗暴但极其有效的手段：模型生成这些词的概率被压到零，就只能往"描述物体"的方向走。第三个方面是容错处理。输入太模糊时模型不应该勉强编造一个类别，而是标记为 unknown；输入明显被截断时直接跳过，避免低质量数据污染下游。Cheng 等人\cite{chain_of_thought} 的发现为这个设计思路提供了理论支持：对大模型来说，清晰说明你要什么格式，比给一堆示例有效得多。

\subsection{GPU 加速}

Ollama 是管线最初使用的本地推理框架，但它内置的 CUDA 12.8 库与服务器驱动 565.57.01 不兼容。虽然 Ollama 声称把模型层"offload 到了 GPU"，实测 nvidia-smi 上只显示 4 MiB 显存占用，实际计算全在 CPU 上，吞吐量只有约 3 tok/s，单场景处理约需 15 分钟。

解决办法是用 llama-cpp-python 替换 Ollama。服务器上装有 CUDA 12.6 的完整工具链（nvcc 12.6、cmake 3.22、gcc 11.4），直接利用这些系统库源码编译 v0.2.90 版本。关键编译参数是 \texttt{-DGGML\_CUDA=on}，CUDA 架构设为 sm\_89（对应 RTX 4090 的 Ada Lovelace 架构）。编译过程中遇到了三个技术细节：系统默认的 nvcc 是 11.5 版本，不支持 RTX 4090 的 sm\_89 架构，需要通过 \texttt{-DCMAKE\_CUDA\_COMPILER} 显式指定 CUDA 12.6 的 nvcc 路径；缺少 OpenMP 库，用 \texttt{-DGGML\_OPENMP=off} 关掉；CMake 4.3 的 CUDA 架构参数格式要求写成 \texttt{89} 而非 \texttt{sm\_89}。

编译完成后，qwen2.5:3b GGUF 模型（Q4\_K\_M 量化，1.9 GB）的全部 29 个 Transformer 层被加载到单张 RTX 4090 的 24 GB 显存中，启动一个 OpenAI 兼容的 HTTP API 服务（端口 8080）。管线的其余代码完全不需要修改，仅将 API 地址从 \texttt{http://127.0.0.1:11434/v1} 改为 \texttt{http://127.0.0.1:8080/v1}。优化后实测推理吞吐量达到 99 tok/s，提升了 33 倍，显存占用 4.2 GB（7B 模型）或 1.9 GB（3B 模型）。

\section{Isaac Sim 验证系统}

\subsection{场景生成}

Isaac Sim 4.5 通过 pip 安装在服务器上，以无头模式运行，使用 Vulkan 渲染后端。场景生成完全基于 Replicator Python API，不依赖图形用户界面。本文设计了四类室内房型模板：起居室（6m×5m，10 个物体）、卧室（4.5m×4m，8 个物体）、厨房（5m×4m，8 个物体）和书房（4m×3.5m，7 个物体）。每类生成 5 个随机化变体，共计 20 个合成场景。

场景生成时引入了三类随机化。物体的位置在房间边界内随机扰动，同时进行碰撞检测以保证物体间距不小于 0.5 米，避免穿透。每个物体的材质颜色从 3 种预设变体中随机选取，例如沙发有三种颜色（灰色、深蓝色、米黄色）。光照的色温在 4500 到 6500 K 之间随机采样，光照强度在 400 到 800 之间随机采样。

\subsection{真值导出}

Isaac Sim 的场景数据以 USD（Universal Scene Description）格式存储，场景中每个物体的坐标、类别和尺寸都可以通过 API 直接查询，位置精度为 0.01 米。物体间的空间关系通过几何规则自动计算：水平距离小于 1.5 米且高度差小于 0.3 米的判定为"next to"，距离在 1.5 到 3.0 米之间的判定为"near"，超出 3 米的按方位角判定前后左右。因为计算过程是纯确定性的，不涉及模型推断，准确率为 100\%。导出格式与 Concept-Graphs 管线的 QA 模板完全一致，两组数据可以直接进行逐项对比。
